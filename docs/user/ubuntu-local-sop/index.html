必要前提：Ansible 需要既有 Kubernetes

目前程式的 ANSIBLE 節點會建立 Kubernetes Job，不支援直接呼叫 Ubuntu 的 ansible-playbook。只安裝 Java、遠端 MariaDB 與本機 Ansible，無法完成這個範例。若沒有可用的叢集、Runner 映像與 PVC，請先完成第 04 節；這不是可用環境變數切換的模式。

02｜遠端 MariaDB：DDL 與必要 DML

2.1　由 DBA 建立專用 database 與帳號

在既有 MariaDB 服務上新增空白、專用 database。將下列模板的三種 CHANGE_ME 全部替換。Host 應是 MariaDB 看得到的 Ubuntu 對外來源 IP（含 NAT 後位址），不是 localhost。兩個密碼請不同。

下載 01-database-and-users.sql

01-database-and-users.sql
-- DBA template: REPLACE every CHANGE_ME value before execution.
-- Use a new dedicated database on the existing MariaDB server.
-- This file contains DDL/DCL; no existing schema is dropped or overwritten.
CREATE DATABASE route_engine_sop CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;
CREATE USER 're_sop_migrate'@'CHANGE_ME_UBUNTU_EGRESS_IP'
 IDENTIFIED BY 'CHANGE_ME_MIGRATION_PASSWORD' REQUIRE SSL;
CREATE USER 're_sop_app'@'CHANGE_ME_UBUNTU_EGRESS_IP'
 IDENTIFIED BY 'CHANGE_ME_APPLICATION_PASSWORD' REQUIRE SSL;
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES, TRIGGER
 ON route_engine_sop.* TO 're_sop_migrate'@'CHANGE_ME_UBUNTU_EGRESS_IP';
GRANT SELECT, INSERT, UPDATE, DELETE
 ON route_engine_sop.* TO 're_sop_app'@'CHANGE_ME_UBUNTU_EGRESS_IP';
-- No FLUSH PRIVILEGES is needed after CREATE USER / GRANT.
-- The migrations contain triggers: DBA must also check binary-log restrictions
-- and DEFINER policy. Keep the migration account as the trigger DEFINER.

這一段含 DDL 與權限設定 DCL。帳號建立交給 DBA；不要把管理員帳號用來啟動 Java。schema migration 會建立 trigger，若遠端啟用 binary log 或限制 DEFINER，DBA 必須依政策代為匯入或授權；不要自行更動整台 DB 的設定。保留 trigger 的 DEFINER 帳號，勿在建表後直接刪除它。

2.2　設定連線並先驗證 TLS

取得 MariaDB CA 檔後，放到 $SOP_HOME/mariadb-ca.pem。請填憑證所涵蓋的 DNS 名稱；下方 db.example.internal 是需替換的範例。

bash

密碼會互動輸入。Ssl_cipher 應有值，SHOW TABLES 應沒有任何表。若連線或驗證失敗，先修正 DNS、CA、來源 IP、port 或權限。

手動 schema 模式必須關閉 Flyway

第 06 節會設定 SPRING_FLYWAY_ENABLED=false。本次沒有建立 flyway_schema_history；若保留預設自動 migration，啟動會遇到非空 schema／缺少歷史紀錄錯誤。不要用 baseline-on-migrate 隨意略過。未來升級由 DBA 依已記錄版本套用新增 migration；若要轉為 Flyway 管理，須先逐項比對 schema，再另行規劃 baseline。

05｜啟動真實 REST 範例服務

REST adapter 使用固定 operation protocol。引擎 POST 的 JSON 含 operationId、direction、operationGeneration、input；對端須回傳相同 operationId 與終態。普通 {"ok":true} 或單純 HTTP 200 並不足以讓引擎判定成功。

回應格式示意，operationId 必須與請求一致
{
  "operationId": "由引擎提供的 UUID",
  "status": "SUCCEEDED",
  "output": {"allowed": true, "message": "Check requested branch"}
}

附件 rest-example.py 使用 Python 標準函式庫，提供 POST /operations 與 GET /operations/{operationId}。相同 operationId 與內容重送會回傳原結果；結果存在 rest-state，重啟服務後仍可查。這些檔案是範例外部服務的 operation 紀錄，不是 Route Engine 的狀態資料庫。

首次建立與草稿 API 為 HTTP 201；發布 API 為 HTTP 200。最後輸出應有 status: "PUBLISHED" 與 version: 1。API 會把 route 的預設版本指到最新發布版；trigger 腳本還會明確指定 routeVersion。

publish.sh 只用於首次建立

8.1　先執行 true 分支

腳本先保存請求 body 與 key，再執行 curl。下列 POST 是真正的觸發方式；QUEUE 代表沒容量時可排隊，HTTP 202 只代表接單，不代表 route 已完成。

下載 trigger.sh

trigger.sh
#!/usr/bin/env bash
set -euo pipefail
: "${SOP_HOME:?請先 source 本機 session.env}" "${API_BASE:?}"
BRANCH=${1:?用法: bash trigger.sh true 或 false}
[[ "$BRANCH" == true || "$BRANCH" == false ]] || { echo '只接受 true 或 false' >&2; exit 2; }
VERSION=$(jq -er '.version' "$SOP_HOME/published.json")
ATTEMPT="$SOP_HOME/requests/$(date -u +%Y%m%dT%H%M%SZ)-$(cat /proc/sys/kernel/random/uuid)"
mkdir -p "$ATTEMPT"
printf '%s\n' "sop-$(cat /proc/sys/kernel/random/uuid)" > "$ATTEMPT/key.txt"
jq -n --argjson version "$VERSION" --argjson run "$BRANCH" \
 '{routeId:"ubuntu-rest-ansible-demo",routeVersion:$version,priority:"NORMAL",admissionMode:"QUEUE",input:{runAnsible:$run}}' \
 > "$ATTEMPT/body.json"
printf '%s\n' "$ATTEMPT" > "$SOP_HOME/last-request.txt"
printf '本次請求已保存在 %s\n' "$ATTEMPT"
curl --fail-with-body --silent --show-error --config "$SOP_HOME/curl-auth.conf" \
  -D "$ATTEMPT/headers.txt" -H 'Content-Type: application/json' \
  -H "Idempotency-Key: $(cat "$ATTEMPT/key.txt")" \
  --data-binary "@$ATTEMPT/body.json" "$API_BASE/executions" > "$ATTEMPT/response.json"
jq . "$ATTEMPT/response.json"
jq -er '.executionId' "$ATTEMPT/response.json" > "$ATTEMPT/execution-id.txt"
bash
source "$SOP_HOME/session.env"
bash "$PROJECT_DIR/docs/user/ubuntu-local-sop/files/trigger.sh" true
cp "$SOP_HOME/last-request.txt" "$SOP_HOME/true-request.txt"

應收到 HTTP 202，body 中有 executionId 與 admission 決策。key、body、response、HTTP headers 均保存在這次的 requests 子目錄。

8.2　查到 SUCCEEDED，且 permit 已釋放

bash

poll.sh 每 2 秒 GET /executions/{id}，最多觀察約 6 分鐘（HTTP 呼叫時間另計）。成功條件是 state=SUCCEEDED 且 permitHeld=false。遇到 RECONCILING、MANUAL_WAIT 或失敗終態會停止觀察並提示檢查；不會自動重送、刪除 Job 或改資料庫。

execution API 不回傳所有 step 明細，因此這裡用 SELECT 查詢，不憑 Job 數量猜測。請先驗證 ID 格式；將上面的 true／false execution 分別檢查。

09｜回應遺失與重送規則

如果 POST /executions 逾時、斷線或回 503，先保留原請求目錄。不要再次執行 trigger.sh，因為那會建立新 key。先用同一 principal 查原 key 的 admission decision：

bash
ATTEMPT=$(cat "$SOP_HOME/last-request.txt")
KEY=$(cat "$ATTEMPT/key.txt")
curl --fail-with-body --silent --show-error --config "$SOP_HOME/curl-auth.conf"   --get --data-urlencode "key=$KEY" "$API_BASE/admission-requests" | jq .

需要重送時，沿用完全相同的 key、body 與認證身分。請確認 ATTEMPT 是那次失去回應的請求，尤其你已經跑過其他分支時。

bash
curl --fail-with-body --silent --show-error --config "$SOP_HOME/curl-auth.conf"   -D "$ATTEMPT/retry-headers.txt" -H 'Content-Type: application/json'   -H "Idempotency-Key: $(cat "$ATTEMPT/key.txt")"   --data-binary "@$ATTEMPT/body.json" "$API_BASE/executions"   > "$ATTEMPT/retry-response.json"
jq . "$ATTEMPT/retry-response.json"
jq -er '.executionId' "$ATTEMPT/retry-response.json" > "$ATTEMPT/execution-id.txt"
# 如果要使用 poll.sh，把該請求目錄重新指定為目前觀察對象。
printf '%s\n' "$ATTEMPT" > "$SOP_HOME/last-request.txt"
bash "$PROJECT_DIR/docs/user/ubuntu-local-sop/files/poll.sh"

同 key、不同 body 會 409。若原本的 NOW_OR_REJECT 因容量而明確被拒絕，原 key 重送仍會回原拒絕；只有明確決定發起另一次工作時，才用新 key。IN_DOUBT 是 operation／incident 狀態，execution 常見為 RECONCILING，permit 會保留；外部結果不明不代表「沒執行」。
