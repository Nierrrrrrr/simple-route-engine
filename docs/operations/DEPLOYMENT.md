# Deployment and isolated build

The supported runtime is one Java21/Spring Boot modular monolith, MariaDB/InnoDB and existing Kubernetes. No workflow service, Redis or new message broker is required. All production deployment remains NOT_AUTHORIZED. Kubernetes manifests are templates and are not applied to a production context.

Use `scripts/env.sh` in WSL Ubuntu with a unique `ROUTE_RUN_ID` and the workspace-local verified tools. `scripts/doctor.sh EVIDENCE_DIR` checks the actual daemon and owned kind cluster, not only PATH. `.gitattributes` fixes text to LF and preserves binary JARs. Do not change global Git settings. Windows worktrees require the explicit Linux Git metadata/worktree paths described in HANDOFF if the gitdir file contains a Windows path.

## Local test and CI

The complete executable M6 entry is `bash scripts/verify-desktop-phase.sh M6 .evidence/desktop/$ROUTE_RUN_ID/M6/recheck-unique`. It creates fresh labelled MariaDB containers, authenticates with temporary test tokens, builds with Maven, runs independent JVM/HTTP/kind/Runner cases and cleans only verified owned resources. `scripts/ci.sh` is the platform-neutral CI entry. Its environment must already have Docker, local tools and the owned kind context, plus the old M5 provenance described below. The current CI entry runs FINAL and requires ROUTE_FINAL_HANDOFF plus ROUTE_FINAL_HANDOFF_RECEIPT from the separate fresh-agent exercise described in ADD_ROUTE. It fails before cumulative execution when that evidence is absent. All CI secrets are disposable fixtures, never enterprise credentials.

`scripts/hardening_build.py` copies Maven inputs and source to a new evidence-owned work directory, packages it and proves input hashes unchanged. That package check explicitly skips tests; the cumulative M0-M6 gate supplies real mandatory tests. It separately builds/runs the deployment image from `config/deployment/Dockerfile`: the same immutable Debian/Python base already used for Runner plus the verified workspace-local JDK and application JAR. Python in this image is a base-image utility, not a new service. Java/Maven dependencies and image pins are in config/versions.json, pom.xml, config/mariadb-image.txt and config/runner/Dockerfile. The Maven dependency tree is recorded by every M1 gate.

## Genuine old-runtime upgrade fixture

`config/upgrade/m5-fixture.json` versions the fixture recipe and accepted artifact provenance. `scripts/hardening_upgrade.py` accepts optional `ROUTE_M5_BASELINE_JAR` pointing to the preserved accepted M5 release JAR. SHA-256 must be 0dbeee3eca2ee43e86d9a97bf089263bd007c722f9b8557ee71f1be901ec6072 and size 48769897. For this desktop run it defaults to the run-local baseline/m5-runtime copy. Portable CI can supply that immutable release artifact or, when no explicit artifact is supplied and the default artifact is absent, build the checked-in config/upgrade/m5-source.tar.gz. scripts/build-m5-baseline.py verifies its pinned archive checksum, extracts into an owned evidence directory, verifies exact accepted source fingerprint437f8be7254c3d2685a87b33c5aaaab0191fdca5814ff7834dde2092bfa89fb5, then builds only historical commit e136e47d4a141247fd39fe485ad636aad5e7fbb8. It records the actual new JAR hash under PINNED_HISTORICAL_SOURCE_REBUILD and never claims byte equality with the accepted artifact. The original artifact mode is EXACT_ACCEPTED_ARTIFACT. An explicit missing/wrong artifact fails closed instead of silently falling back. The source archive includes no Git metadata, cache or evidence; current candidate engine sources are never used as the old runtime. The M6 clean-build suite actually rebuilds this archived source, and a second upgrade fixture runs the reconstructed JAR before upgrading to the candidate.

The fixture starts that old JAR against a fresh DB and controlled HTTP catalog, publishes routes and creates QUEUED and MANUAL_WAIT via real APIs. After stopping the old process it launches the candidate, verifies V1-V7 plus additive V8, compares exact published definition/binding rows and execution snapshots, then resumes queue and recovery. The old catalog is not retargeted between versions. A new engine semantic version must explicitly support old versions or fail closed. Never rewrite accepted migrations or published definitions. Rollback to the old executable after a DB upgrade requires an explicitly tested migration compatibility plan; no destructive down-migration is supplied.

## Undeployed application template

Build: `python3 -B scripts/build-app-image.py .evidence/desktop/$ROUTE_RUN_ID/app-image` after the normal verified JAR build and JDK bootstrap with scripts/env.sh. It copies the actual JDK (dereferencing the local java symlink) and JAR into a dedicated build context. Publish images only with separate authorization. Resolve the resulting registry digest and render, without applying:

    python3 -B scripts/render-deployment.py route-engine-work registry.example/route-engine@sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef .evidence/deployment.json

The digest above is an illustrative syntax value, not a deployable published image. The renderer rejects tags without digests. The template has one replica/Recreate, nonroot/read-only filesystem, bounded resources, readiness including DB, graceful termination and a persistent log PVC. Create namespace/ServiceAccount, logs PVC, catalog ConfigMap and Secret references using an authorized deployment process. `route-engine-runtime` provides ROUTE_DB_URL/USER/PASSWORD and the three token-hash variables; mount the explicit adapter kubeconfig and credential files through `route-engine-adapter-identity`. The catalog points at `/run/adapter` references. Workload artifacts use their own pre-created PVC as configured by AdapterCatalog, not the application log volume. Use `config/kubernetes/adapter-role.yaml` for the work namespace; deny Secrets, exec and other namespaces. The engine Pod does not auto-mount a service-account token.

## Backup and restore

The M6 test `hardening_processes.acceptance` performs an actual transaction-consistent mariadb-dump and restore into a distinct fresh labelled MariaDB, comparing route definitions, executions and append-only audit counts. Raw commands, dump SHA, restore exit and comparison rows are preserved in M6 processes evidence. The test database contains only synthetic data. Operators must apply their approved DB backup retention/encryption policy, capture a consistent DB backup with the matching external artifact PVC snapshot, and rehearse restore in a separate isolated environment before any production change. Never restore over the active database or infer external operation absence from a restored row. Retain original external identities and reconcile before enabling admission.

The local demo helper accepts only parsed http://127.0.0.1:<port> origins without userinfo, path, query or fragment, and refuses redirects before forwarding credentials. Use synthetic local fixture credentials.
